# 参赛材料 · 开发过程与 AI 协作说明

> 用途：对应评分表「**AI 工具使用 25%**」
> 说明：本文档是**导读与证据索引**，原始对话记录见 LearnBuddy 历史对话（随材料一同提交）
> 原则：如实呈现协作方式——**人负责判断，AI 负责实现**，每一步都有可验证的结果

---

## 一、协作模式：人定方向，AI 落地，人逐项验收

| 环节 | 谁做 | 具体表现 |
|---|---|---|
| **需求定义** | 人 | 决定做什么、不做什么："面向大学理工科"、"讲解要讲透而不是给答案"、"错题要能按遗忘曲线复习"、"老师批改要能省时间" |
| **方案取舍** | 人 | 拍板关键决策（例：否决"合并调用"的批改方案、决定不做题库众包入口而改做命中率优化） |
| **实现** | **AI（LearnBuddy）** | 需求翻译、架构设计、编码、测试脚本编写、部署执行、文档撰写、数据诊断 |
| **验收** | 人 | 逐项检查、指出问题、要求返工（例："这个功能和那个功能有什么区别"、"这些东西有什么用"） |
| **领域判断** | 人 | 教育场景的合理性（判分标准、掌握度规则、成就体系尺度） |

**一句话**：项目里**没有一行代码是 AI 自己决定要写的**——每个功能都来自人的需求，每次方案选择都由人拍板，每个交付物都由人验收。AI 的价值是把这个过程的速度提高了数倍。

## 三、六个典型协作片段（每个都有可验证的结果）

### 片段 1 · 让错题真正形成闭环

- **人的需求**："测试错的题要能进错题本，下次自测还能练到。"
- **AI 的动作**：先给出实现方案（勾选入本 / 自动入本 / 全部入本三种做法与取舍）→ 按确认的方案实现 → 写端到端验证脚本（**11/11 通过**，含重复入本去重）→ 部署上线
- **人的验收**：检查是否与现有 SRS 规则冲突、是否会产生重复条目
- **结果**：班级测试的错题自动沉淀到个人错题本，与自测复习打通

### 片段 2 · 批改从"守着看"变成"关页面也能跑"

- **人的需求**："几十份作业，老师不能一直守着页面。"
- **AI 的动作**：先出方案（后端任务表 + 线程池并发 3 + 进度轮询），说明为什么用内存任务表而不新建表 → 实现 → 端到端验证 **12/12**
- **过程中的真实插曲**：任务表键不一致导致**进度恒为 0**（批改其实在跑、结果也落库了）。AI 是从"结果已落库"这条断言通过、而"进度推进"失败这个**矛盾**反推定位的
- **结果**：老师发起批改后可关闭页面，回来能看到进度、剩余时间预估与失败名单

### 片段 3 · 一个"看起来更先进"的方案被数据否决

- **背景**：AI 提出把"转录 + 判分"两次模型调用合并成一次，直觉上更省、更快
- **人的决策**："用真实数据测一遍再定。"
- **AI 的动作**：设计 A/B 实测（3 个样本，含 2 个构造的边界样本；各跑 2 次，共 **20 次真实模型调用**），结论：
  - 判分结果完全相同（95 / 95）
  - 转录文本**逐字相同**（131 字）
  - 单份耗时 **7.5s → 277.5s**（高一个量级），且一次失败整份重来
- **人的决策**：不采用新方案；转而做零成本的"纸面信息增强"（让转录带 `{涂改}`/`{空白}` 标记）
- **结果**：避免了一次"看起来更优"的性能倒退

### 片段 4 · 盘出一个"只进不出"的题库

- **背景**：题库设计是"AI 讲解完自动回填、下次同题复用"，但实际没人用上
- **AI 的诊断**：线上 **273 条题目，命中次数全部为 0** → 根因是匹配要求相似度 ≥ 0.96（近乎逐字相同），而拍照识别与公式写法差异让同一道题掉到 0.55~0.86
- **人的决策**：确认改做"命中率救活"，**不做**题库众包入口（用户贡献解决不了匹配问题）
- **AI 的动作**：归一化增强（去标点 / 剥题号 / LaTeX 命令等价化 / Unicode 数学符号映射）+ 阈值 0.96→0.90 + 数字指纹剥题号 → 离线断言 **12/12** + 线上真实库复验命中
- **结果**：同一道题的不同写法命中率 **0.545→1.000**（LaTeX 写法 0.444→0.947），不同题仍正确拦截

### 片段 5 · 一个 bug 教会的排查方法

- **现象**：新功能上线后弹窗打不开，报 `Cannot read properties of undefined (reading 'slice')`
- **AI 的前两轮**：按猜测加了防御式取值、修了数据取值用法 —— **都没解决**
- **转折**：AI 改为**直接读构建产物**，在压缩代码里定位到报错偏移，一眼看到根因是模板用了 `d.date`，而数据实际返回的字段叫 `label`
- **人的作用**：要求"不要猜，找到确凿证据"（这正是 AI 前两轮失败的原因）
- **结果**：一处替换即修复；这条"压缩产物里的运行时错误要直接读产物定位"的教训被写进了项目约定文档

### 片段 6 · 首屏优化：先找真因，再动手

- **人的需求**："打开有点慢。"
- **AI 的诊断**：没有按"拆包"这个常见套路走，而是先测出真凶——`index.html` 里 4 个同步脚本（约 396KB）阻塞首屏，**路由其实已经分包了**
- **AI 的动作**：按需注入重库 + 调用点降级（拿不到库就退化为纯文本域）→ 复测
- **结果**：首页可用时间 **3990ms → 1618ms（−59%）**，传输量 −44%

## 四、AI 具体被用在哪（分层）

| 层次 | 具体用途 |
|---|---|
| **需求翻译** | 把"讲解要讲透"落成结构化讲解字段（最终答案 / 解题步骤 / 知识点 / 易错点） |
| **方案设计** | 批改任务化、SSE 实时推送、题库命中判定、按需加载——都先出方案再实现 |
| **编码实现** | 前端 26 页面 / 30 个自研 UI 组件；后端 73 个接口 / 25 张表 |
| **测试编写** | 112 个测试与验证脚本（离线断言 + 端到端浏览器验证），关键改动都有回归 |
| **部署执行** | 构建、上传、服务重启、线上冒烟（19 条路由逐页检查） |
| **数据诊断** | 线上题库命中诊断、首屏性能基线、批改耗时测量 |
| **文档撰写** | 仓库约定、任务表、技术亮点、参赛材料 |

## 五、人做了哪些"AI 替不了"的事

1. **定义问题**：AI 不会自己想到"学生课后没人讲、错题不回头、老师批完沉淀不出学情"这三件事要一起解决
2. **拍板取舍**：否决 A/B 测试里更"优雅"的方案、决定不做众包、决定优先做命中率
3. **验收标准**：要求"每个改动都要有可复现的验证"，最终积累出 112 个测试脚本
4. **领域判断**：判分标准、掌握度规则（连续对 2 次才算掌握）、成就体系的尺度
5. **质量把关**：指出模糊之处、要求返工（本项目中 AI 有两轮"按猜测修 bug"被要求改用证据定位）

## 六、这套协作方式的可复用点（供参考）

| 做法 | 为什么有效 |
|---|---|
| **先出方案，确认后再动手** | 避免 AI 在错误方向上做大量无用功 |
| **每个功能都配端到端验证** | 让"完成"有客观标准，而不是"看起来能用" |
| **纯逻辑与 UI 分离，先写离线断言** | 复杂规则（SRS 排期、命中判定、数据聚合）可以脱离网络快速回归 |
| **用真实数据做决策** | A/B 实测、命中率诊断、性能基线——避免"感觉更快了" |
| **出错时找证据，不要猜** | 压缩产物的报错直接读产物定位，比按猜测改快得多 |
| **把踩过的坑写进文档** | 项目约定文档里累积了十余条实测教训，避免重复犯错 |
