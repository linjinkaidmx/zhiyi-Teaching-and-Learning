# 批改 V1 / V2 A/B 实测结论

> 实测时间：2026-09-22 晚 · 样本：3 份 · 每版每样本 2 次 · 共 20 次模型调用
> V1（现状）= 视觉转录（doubao-seed）+ 文本判分（deepseek-chat），2 次调用
> V2（候选）= 一次视觉调用同时输出「转录 + 逐题判定」，1 次调用

## 一、样本与结果

| 样本 | 说明 | V1（两段式） | V2（合并一次） |
|---|---|---|---|
| **S1** | 线上真实手写作业图（49KB，完整解答） | 分数 **95 / 95**<br>转录 131 字（两次逐字一致）<br>耗时 **7.5s / 8.2s** | 分数 **95**<br>转录 131 字（**与 V1 逐字一致**）<br>耗时 **277.5s** |
| **S2** | 合成图：只写答案不写步骤（跳步） | 分数 **60 / 70**<br>评语准确指出「只给答案不给过程，属跳步丢分」<br>耗时 185.3s / 83.3s | 未单独跑（S3 显示大图下合并调用更易超时） |
| **S3** | 合成图：有涂改 + 符号潦草（93KB） | **超时 ×2** | **超时 ×1** |

## 二、四个关键结论

**1. V2 在判分质量上没有增量。**
同一份作业，V2 产出的转录与 V1 **逐字相同**（131 字）、分数相同（95），唯一多出的是评语里一句"书写工整清晰"。而作业评分标准是**正确性**，书写不打分，所以这句话不影响分数。

**2. V1 并不存在"看不到纸面问题"的失效。**
这是本次实测最有价值的一点：在跳步样本（S2）上，V1 的转录里天然就没有推导过程，判分模型据此**准确识别出"跳步丢分"**并给出 60/70 分与精准评语。也就是说，V2 主张的核心卖点（"能看出步骤不完整"），V1 已经能做到。

**3. V2 的代价是确定性的、且不小。**
- 同一张图：V2 **277.5s** vs V1 **7.5s**（V2 首次调用很可能 180s 超时后重试才成功）
- 一次调用同时承担转录与判分，**任何一环失败则整份重来**（V1 的转录可缓存复用、单步可重试）
- prompt 更长、输出更长 → 更容易超时或输出被截断

**4. 真正拖慢批改的不是 V1/V2，而是图片本身。**
- 同样的代码路径：49KB 真实图 **7.5s**；93KB 合成图 **两版都超时**
- 项目对作业图的压缩上限是 **450KB** —— 真实用户随手拍的手机会接近这个量级
- 这解释了"多人作业慢"的根因：**不是流程串行（已并行化），而是单张图的视觉调用本身慢且不稳定**

## 三、建议（不切 V2，改做三件更值的事）

| 优先级 | 动作 | 收益 | 成本 |
|---|---|---|---|
| **P0** | **作业图预压缩更激进**（长边限 1600px、质量 75，目标 200KB 内） | 直接压缩单份批改耗时，减少超时 | 后端一处压缩参数 |
| **P0** | **批改超时与重试策略**：服务端超时放宽 + 失败自动重试 1 次 + 前端显示"已用 x 秒" | 消除"卡住不出结果"的体验断点 | 小 |
| **P1** | **给 V1 的转录提示词加一句**："若有涂改/划掉/空白未写，用 `{涂改}` 标注位置" | 判分模型获得纸面线索，**零额外调用、耗时与成本不变** | 一行 prompt |
| 已做 | 并发 3 批改（本日已上线） | 多份作业总耗时下降 | — |

**不建议**：切换到 V2 的"一次视觉调用"方案 —— 质量无增量、耗时与失败风险显著上升。
